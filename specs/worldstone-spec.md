# WorldStone — Product Specification

Status: living document. Last verified against upstream: 2026-09-28. Update it when a milestone lands or a decision changes.

## 1. Purpose

WorldStone is a Windows desktop app that turns "I want a **Vanilla** World of Warcraft private server with **playerbots**" into a working, running server without the user touching Git, Docker, SQL, CMake or config files. It fetches the emulator, builds it, extracts client data, provisions the database, configures everything, runs it in Docker and proves it works.

**The headline goal: playerbots are built in, switched on, and demonstrably working.** A server that starts but has no bots online is not done.

## 2. Non-negotiable principles

1. **The app does the work. Claude does not.** Every step in §5 must be performed by WorldStone's own code, driven by its buttons. If a step can only be finished by someone running commands by hand, that is a bug in the app, and the step is not done. Development work never hand-runs a pipeline step and calls the result verified.
2. **Every control works.** No placeholder buttons, no dead nav entries, no "coming soon" pages. A control appears only when the code behind it exists and passes its acceptance test (§9). A control that cannot run right now is disabled and says why.
3. **Real state only.** Status, progress, counts and health come from the running system (Git, Docker, the database, the server's logs). Unknown is shown as unknown. Progress bars show only what a tool reported; otherwise indeterminate. **Fast never means stale**: a status is read from the system when it is asked for; the only reuse allowed is the one rule in §5, Step 0 ("Reading Docker").
4. **Follow how these servers are really set up.** The sequence and settings follow upstream's official material (§3), including the order the official database installer applies SQL. Where WorldStone deliberately differs (§3.2) it says why.
5. **Safe by default.** Never delete, reset or overwrite user data silently. Back up before database updates. Stage before replacing. Generated credentials, localhost-only ports by default, nothing secret in logs.
6. **Resumable and idempotent.** Every step can be interrupted and run again. Re-running a finished step is a fast no-op.
7. **The user supplies their own client.** WorldStone never downloads game files.

## 4. Scope and emulators

**Now: Vanilla WoW (1.12.x) only. Later: multiple emulators and expansions, added by the project owner.** The product is built as a multi-emulator, multi-instance tool from day one (§6); only the Vanilla recipe is *implemented* until it passes the §9 acceptance run.

The AzerothCore recipe passes §9 only when the acceptance run is done in the real app with a real 3.3.5a client; until then it is listed *Implementing*, and each Step below says what was and was not exercised for it.

## 5. The pipeline (MaNGOS Zero)

Each step lists what the app does, what "done" means, and how it fails safely. Steps run in order; the UI shows each one's real state and offers exactly the actions that make sense.

### Step 0 — Environment
- **Checks:** Git; Docker CLI; Docker engine running with **Linux containers**; Compose; enough free disk (build + client data + database; measured, not guessed); ports 3724 and 8085 free on localhost; Docker memory sufficient to compile (detected; parallelism scaled to it).
- **Actions:** Re-check. Where a fix is available through the app (for example installing Git or Docker Desktop via winget), a button does it, with confirmation.
- **Done when:** all required checks are Ready. Warnings explain the fix.
- **Reading Docker (all steps' status cards).** A status is a *read*, so it asks Docker's own engine API on the local named pipe (`dockerapi.rs`, endpoint resolved the way the `docker` program resolves it: `DOCKER_HOST`, then the current context, then the default) instead of starting a `docker` process per question (5–70 ms against 330–600 ms). `docker.rs` is the app's vocabulary over it (engine, image, container, volume, container list, exec, reading files out of a volume). When the engine is not on a local pipe (a remote `DOCKER_HOST`, for example) each function falls back to the `docker` program, which prints the same JSON, so both routes use one parser. Changes (build, start, stop, import, extraction, remove) still go through `process.rs` and the `docker` program.
  - **Freshness rule.** Per-object reads (a container's state, an image, a volume) are never reused. The engine's facts and the container lists, which several cards ask for at once, share one read only while all of these hold: it is under 400 ms old, it began after the last time this app ran any `docker` program (`dockerapi::invalidate`, called around every `docker` run in `process.rs`), and nothing else changed. So a card never shows a state from before an action of the app; an outside change (a person using Docker Desktop) shows within 400 ms.
  - **Reading the extraction record** needs no container run: a container is created from the tools image with the data volume attached read-only, never started, the record is read from it as an archive, and it is removed at once (fixed name `worldstone-<instance>-reader`, one at a time).
  - **SQL from status reads** runs as an API exec in the database container; the password reaches it through the exec's environment, never the command line or a log.
  - **Versions** of Git, Docker and Compose are asked again only when the program file (its path, size and write time) or, for Compose, the engine's version changes.
  - Not yet done through the API: container logs and resource use (they stream, and are only read on their own pages).

### Step 1 — Source *(implemented)*
- Clones `server` and `database` **with all submodules** (`dep`, `src/realmd`, `src/modules/SD3`, `src/modules/Eluna`, `win`; and the database's `Realm`). Update fast-forwards only, then updates submodules.
- **Done when:** both checkouts are on the recipe branch and every submodule is checked out. A checkout missing a submodule is reported *Incomplete* and repaired by the next Download/Update.
- **Safe:** never resets local edits; refuses to switch branches; never deletes a folder that is not a Git checkout; a clone is staged in `Temp` and moved into place when complete.

### Step 2 — Build *(implemented and verified)*
- **Actions:** *Build server* and *Rebuild server*. The build runs in a container from a Dockerfile **generated from the recipe** (`Instances/<id>/Docker/build/Dockerfile`, with a `.dockerignore` that keeps `.git` out of the context, as upstream's does). The base image, compiler, apt packages, install prefix and CMake options all come from the recipe. For Zero that is upstream's own choice (Ubuntu 22.04, clang, `/mangos`) with `-DCMAKE_BUILD_TYPE=Release -DBUILD_TOOLS=ON -DBUILD_MANGOSD=ON -DBUILD_REALMD=ON -DSCRIPT_LIB_ELUNA=ON -DSCRIPT_LIB_SD3=ON -DPLAYERBOTS=ON -DPCH=OFF -DBUILD_AH_SERVICE=OFF`. The result is **one image per server**, named `worldstone/<edition>-<role>` from two recipe fields (`edition = "vanilla"`, and each service's `role`): `worldstone/vanilla-realm` and `worldstone/vanilla-world`, each tagged only `latest` so Docker Desktop lists every server once under a name that says what it is (a second instance of the same recipe adds its instance name: `worldstone/vanilla-<instance>-world`). Both are final stages of the one generated Dockerfile (`FROM runtime AS service-<id>`, labelled `io.worldstone.edition` and `io.worldstone.role`, default program the service's binary), so they hold the same install (`mangosd`, `realmd`, the extractor and the `.dist` configs), share every layer and cost no extra disk; the compile happens once and the second `docker build` is cached. The extractor and the configuration step read the tools and `.dist` files from the image of the service that reads the client data (the world server). The database image is the recipe's public `mariadb:11.4`, given the name `worldstone/vanilla-database:11.4` by the database step (`docker tag`, the tag keeps the public version): the step downloads the public image if it is missing, names it, and drops the public name with `docker image rm` (which only removes the name) unless another container uses it. Compose runs the database from the local name with `pull_policy: never`, and *Start servers* asks for *Start database* first if the name is missing.
- **The images are the record.** A fingerprint of the generated Dockerfile plus the exact source (commit, every submodule commit, uncommitted and untracked edits) is stored as a label on each image, together with the commit, recipe and instance (there is deliberately no second, code-named tag: it showed up as a duplicate row in Docker Desktop). *Build* is a no-op when every server image carries the current fingerprint; the state shown in the UI (*Not built / Ready / Outdated*) is read from Docker, so it cannot drift from a separate lockfile. *Rebuild* ignores the cache and re-pulls the base image.
- **Parallelism** is chosen from the Docker VM's CPUs and memory (one job per CPU, at most one per 1.5 GiB above 2 GiB) and passed as a build argument, so it never invalidates the cache. A compiler cache (ccache) is mounted between builds, **but measured hit rate on an incremental build was only ~6% (416 s against ~480 s cold), so source updates are not yet faster; open issue.**
- **Progress** is CMake's own `[ 45%]` count from the build output; other phases are indeterminate.
- **Done when (checked by the Dockerfile itself, so a failing image is never tagged, and re-checked from outside on every Build):** every recipe `required_files` entry exists; **the playerbots marker file `etc/aiplayerbot.conf.dist` exists** (it is installed only when bots are compiled in); each recipe smoke command runs and exits 0 in the image (`mangosd --version`, `realmd --version`, which also proves every runtime library is present).
- **Failure:** out-of-memory (a killed compiler, exit 137) is detected in the output and the build **retries automatically with half the jobs**, down to one, reusing finished work; only then does it tell the user to raise Docker Desktop's memory. Otherwise the message names the last compiler, CMake or apt error; the full output stays in the log. The build can be cancelled at any time. Cancellation **interrupts** the child (Ctrl+Break to its own process group, then a kill after a grace period) because killing `docker.exe` outright left BuildKit compiling for minutes; verified against the real Docker engine.
- **Blocked, with the reason shown beside the button:** Docker not running or in Windows-container mode; source not downloaded or incomplete.

### Step 3 — Client data *(implemented and verified)*
- **Input:** the folder of the user's own 1.12.x client, chosen with the system folder picker (*Choose client*, on Home and Setup) or pasted on the Setup page. The recipe declares what a usable client is (`[client]`): `WoW.exe` present with a file version whose build is one of 5875 (1.12.1), 6005 (1.12.2) or 6141 (1.12.3), read from the executable's own version resource (never guessed from the folder name); the `Data` folder with the base archives present; a locale folder is reported when there is one, and a client whose language is merged into `Data` is accepted. Pointing at the `Data` folder itself is corrected to its parent. Anything else is refused with the reason and the list of supported versions. **Only a client that passes is remembered** (`Instances/<id>/Config/client.json`); a remembered folder that later stops passing is shown with the reason, not silently forgotten.
- **Actions:** *Extract client data* / *Resume extraction* / *Extract again*. The client is mounted **read-only** into a container from the built image and the recipe's own extractor is run once per phase, in the tool's own order: `dbc` (client databases), `gomodels` (game object models), `trans` (ship decks), `tile` (world tiles), `nav` (movement maps). `nav` needs the tiles and `tile`/`trans` need the models, so the order is not arbitrary. Shared options: `--src`, `--dest`, `--threads` (scaled to Docker's CPUs and memory), `--no-menu` (so it never waits for input), and the tool's own `vessels.txt` and `offmesh.txt`. Output folders the server reads: `dbc/`, `tiles/`, `gomodels/`, `mmaps/`.
- **Where it lives.** A Docker volume per instance, `worldstone-<instance>-gamedata`, holding `current/` (the data in use, with `.worldstone-extract.json`: client build and version, extractor commit, time taken, file count and size per folder), `staging/` (a run in progress, with a `.done/<phase>` marker per finished phase and a `.session` of image fingerprint, client build and path) and `previous/` (the last good copy). A Docker volume, not a Windows folder, because the server container reads thousands of small files and a bind mount across the WSL boundary is slow. The state shown in the UI is read from that record, so it cannot drift from a separate lockfile.
- **Safe:** extraction always writes to `staging/`; `current/` is replaced only after every output folder is verified to hold files, by renaming (`current` → `previous`, `staging` → `current`), so a failed or cancelled run never touches good data. An interrupted run is resumed: finished phases are skipped when the image, client build and client path are unchanged, otherwise staging is cleared and it starts fresh. The client folder is never written to.
- **Progress** is real: the step (`Step 4 of 5: World tiles`) and the tool's own per-map lines counted as they arrive (`43 maps done`; for movement maps the tool reports its own total, `7 of 51 maps done`). The extractor prints no percent, so there is no percent bar and no invented estimate.
- **Cancel** stops the container at once and keeps the finished phases; the phase that was running is redone on resume (movement-map work in progress is lost).
- **Failure:** an out-of-memory kill (exit 137) retries the phase with half the threads, down to one, then says to raise Docker Desktop's memory; other failures name the phase and the last output lines. The full output stays in the log.
- **Blocked, with the reason shown beside the button:** no server image yet, no valid client chosen, Docker unavailable.
- **Done when:** the extractor exited 0 for every phase, all four folders hold files, and the record is written and promoted. The bots' pathing depends on movement data, so `mmaps` is required, not optional.
- **Known limits:** one previous copy is kept; a source update that changes the extractor's output format is not detected beyond the extractor commit recorded with the data (the record shows it); closing the app mid-extraction leaves the container to be removed by the next run.

### Step 4 — Database *(implemented and verified)*
Follows the official `InstallDatabases.sh` order, implemented by WorldStone with an idempotent ledger (a `worldstone` schema in the same database records what has been loaded; the schemas' own `db_version` rows are what decides which updates are pending):
1. Start MariaDB (named volume/bind under `Data/mysql`); wait until healthy.
2. Create the `mangos` user (generated password) and the three schemas: **`realmd`**, **`character0`**, **`mangos0`**, granting only on those.
3. For each schema: run `*CreateDB.sql` if needed, load `*LoadDB.sql`. (The Character load includes the `ai_playerbot_*` tables.)
4. World "populated" load: every file in `World/Setup/FullDB/`.
5. Apply updates from `Updates/Rel21` then `Updates/Rel22` for Character, World and Realm, in filename order, **skipping any at or below the schema's current `db_version`**. A failed update stops the run, keeps the backup, and reports the file.
6. Add the realm entry (upstream's `Tools/updateRealm.sql` logic) with builds `5875 6005 6141` and the address chosen in Step 7.
- **Safe:** never reload base SQL into an existing schema; mysqldump backup before any update; an interrupted first import is preserved and reported, never auto-reset.
- **Done when:** each schema's `db_version` matches the newest update file, the realm row exists, and bot tables exist in `character0`.

### Step 5 — Configuration *(implemented and verified)*
- **Generate / Update configuration** writes `Config/server/{realmd,mangosd,aiplayerbot}.conf` from the `.dist` samples inside the built image. Managed keys (declared per file in the recipe): the database connection strings (generated password), `RealmID`, `DataDir`, `LogsDir`, ports, `PlayerLimit`, `Console.Enable`, `GmLogFile` (emptied, see Step 7), `PlayerbotAI.DisableBots = 0` and the bot keys in Step 8. A managed key that is a commented sample is uncommented; one that is absent is appended. **Everything else in the files is preserved**, so a hand-edited key survives; a hand-edit of a *managed* key is overwritten on the next run (those values come from `Config/settings.json`, which the bot settings on the Play page write).
- `Config/settings.json` holds the choices behind the managed values (realm id, bots on/off, min, max). It is created with defaults for this machine the first time and never overwritten.
- The files are mounted read-only into the server containers. Status is read from the files themselves: *Missing / Outdated (names the keys, never the values) / Ready*. Blocked with a reason until the image, the client data and the database exist.
- **Done when:** the files exist and every managed key has the intended value.

### Step 6 — Run *(implemented and verified)*
- Compose services generated per instance (`Docker/compose.yml`): `database` (never published on the host), `realmd` (3724) and `mangosd` (8085, stdin open so the console is reachable), from the image built in Step 2, with `pull_policy: never`. Ports are published on `127.0.0.1` only. `mangosd` mounts the extracted client data read-only. Each server's health check is a TCP connect to its own port inside the container, so *healthy* means the server is listening; `mangosd` only listens after the world has finished loading. The database is healthy before either server starts.
- **Actions:** *Start* (brings up the database, then the servers, and shows the newest log line of the current run while it waits, up to 20 minutes for a first start; then checks the ports from this machine), *Stop* (servers first, the world server saves and exits, then the database; a non-zero exit code is reported as "not cleanly"), *Restart*. *Start* recreates containers that differ from the compose file, and never touches volumes; putting right everything else that is wrong is the separate *Repair* (Step 9).
- **Pause / Resume:** *Pause* freezes the realm and world servers with `docker compose pause` (a Docker cgroup freeze): the processes stay in memory, the world stops advancing, nobody can log in or keep playing until *Resume*, and **nothing is saved or closed**. The database keeps running. It is offered only while both servers are running, and the state is read from Docker (`paused`), never remembered, so a freeze survives an app restart and is shown as *Paused* on the Servers card (bots: *stopped*, *frozen with the world server*). *Resume* runs `docker compose unpause` and waits until both ports answer again; players usually have to log in again because their connections timed out. *Start* refuses while paused (resume or stop instead), and *Stop* / *Restart* resume the frozen servers first, because a frozen world server cannot save or answer a stop.
- Start is cancellable and stops what it started if cancelled. Status is read from Docker (missing, stopped, starting, running, unresponsive, crashed with exit code) plus a real port check, and refreshes every 10 s.
- **Done when:** both ports accept connections. (The console is used from Step 7.)

### Step 7 — Accounts and connecting *(implemented; verified in the real app except the realm-list write)*
The **Play** page has three sections: connect, accounts, bots.
- **Accounts** are created and changed through the world server's console (`account create`, `account set password`, `account set gmlevel`; the templates are in the recipe's `[accounts]` section), the official mechanism. The console is fed through `docker exec -i … sh -c 'cat > /proc/1/fd/0'` with the line on stdin, so a password is never in a process argument; **never close the container's stdin**, because the world server treats end-of-input as a shutdown request. The result is confirmed by reading `realmd.account` (a created name exists; a changed password matches `SHA1(UPPER(name):UPPER(password))` computed inside the database), never from the console's wording; when it does not, the reason is the server's own reply from the log of the current run. Needs the servers running.
- **Rules:** names are letters and digits, at most 16, stored upper-case, and may not start with `RNDBOT` (the bots' own accounts). Passwords are at most 16 visible ASCII characters without spaces, quotes, backslashes, backticks or braces (the client cannot type more than 16; the rest would be read specially by the console or the templates); there is **no minimum length**. **A new account needs only a name:** with the password left blank the account's own name becomes its password (the console cannot take an empty one), the form says so before it is sent, and the log says *with its name as the password*; the list then flags the account as having a default password, so it can be changed later. Changing a password does need one. A **Generate** button makes a 12-character password from the browser's cryptographic random source without look-alike characters; the password is shown in the form so it can be typed into the game, is not stored, and is not written to any log.
- **Confirmation:** when a create task ends well (not when it is merely started), a green *Account NAME created.* notice with a check mark appears beside the button and the form's border turns green; it stays about 2 s and fades out over 0.7 s. It is not shown again when the page is left and reopened. A failure is not hidden by it: the error banner and the task panel say why.
- **The server's own GM log is switched off** (`GmLogFile` empty): it records every console command as typed, and `account create` carries the password. Found while verifying; nothing else on disk or in `docker logs` contained it.
- **Default accounts:** the emulator's database ships `ADMINISTRATOR`, `GAMEMASTER`, `MODERATOR` and `PLAYER`, each with its own name as password. The list flags any account whose password still equals its name (checked in SQL, not by trusting the row) and offers **Change password**.
- **Connect client:** the client's `realmlist.wtf` is found through the client folder from Step 3 (the remembered one). Only the `set realmlist <address>` line changes; other lines, line endings and any BOM stay as they are. The old address is saved beside it first as `realmlist.wtf.worldstone-backup` (numbered `.2`, `.3` when a different address would be saved later; a saved copy is never overwritten; identical content is not saved twice). **Restore** puts back only the saved address and then removes that copy. Files are written through a temporary file and a rename. States: no client, unknown, no file, pointed here, points elsewhere.
- **Launch game:** starts the chosen client's executable (`WoW.exe` for Zero, from the recipe) from its own folder, as a program of its own: it is not tied to this app and stays open if the app closes. It is refused, with the reason, unless a usable client is chosen and **both servers are running** (not starting, paused, stopped or failing). It first does what *Point client* does (a no-op when the file already points here; otherwise the old address is saved first, as above, and *Restore* undoes it), and logs that step, so the button never edits the client silently. After starting it waits about 2.5 s: a game that has already exited is reported with its exit code instead of as started. The process is spawned only through `process.rs`.
- **Realm address:** `127.0.0.1` for now, because the ports are published on this machine only. Exposing the server to the LAN or the internet (a chosen address, the realm row, a warning) is deferred to Milestone 8.
- **Done when:** the created account can be found in `realmd.account` and the client realmlist points at the server.

### Step 8 — Playerbots *(the headline requirement)*
- **Always built** (`PLAYERBOTS=ON`). **Always configured on** (keys as `PlayerbotAIConfig.cpp` reads them): `AiPlayerbot.Enabled = 1`, `AiPlayerbot.RandomBotAutologin = 1`, `AiPlayerbot.RandomBotLoginAtStartup = 1`; `RandomBotMaps = 0,1` comes from the dist file. The bots create their own accounts (`rndbot0`, `rndbot1`, … flagged `playerbot = 1`) and one character per class, so `RandomBotAccountCount` × 9 bounds the roster.
- **Population is user-tunable** in the UI: `MinRandomBots`, `MaxRandomBots` and `RandomBotAccountCount` (derived from the maximum with a margin). Defaults are scaled to the machine's CPU and memory (8 bots per CPU or per GiB of Docker memory, whichever is lower, between 40 and 200; minimum half of that) rather than upstream's 50–200 guess. The Play page changes on/off, minimum and maximum; a maximum level setting is not exposed yet.
- **Player limit:** `PlayerLimit` (upstream default 100) is raised above `MaxRandomBots` plus reserved real-player slots, because a roster larger than the cap would silently stall the bot count. The app verifies this rather than trusting it (see health below).
- **Health, from real data**, shown in a Bots panel:
  - *Built in:* `aiplayerbot.conf.dist` present in the install.
  - *Enabled:* the managed keys have the intended values.
  - *Creating:* bot accounts in `realmd.account` (prefix `RNDBOT`) and bot characters in `character0` are increasing. First launch creates the roster and can take a long time; the panel shows the real counts.
  - *Online:* count of bot characters with `online = 1`.
  - *Stalled:* the online count stops short of `MinRandomBots` for a defined period → the panel names the likely cause (player limit, no bot characters, too few characters, or the newest `ERROR`/`FATAL` line of the current log run).
  - The state is **derived from the database and the world server's uptime each time** (nothing is remembered between reads): *unknown, off, stopped, starting, creating, logging in, online, stalled*. Bots are *online* when the online count is at least the minimum and above zero; the first 10 minutes after the world server starts are a grace period (*starting / creating / logging in*), after which a shortfall is *stalled*.
  - **Restart needed:** shown when a server that is up started before the newest `Config/server/*.conf` change; the Restart servers button is offered next to it.
- **Controls:** on/off, minimum and maximum, saved through **Save bot settings** (writes `Config/settings.json`, regenerates the config from it, nothing else; the servers read it at the next start, so it does not restart them silently). There is no separate *restart bots* or live console action: the bots are driven by configuration only.
- **Done when:** after Start with a clean install, the online bot count reaches the configured minimum, it survives a restart, and a real client account can log in and see bots in the world.

### Step 9 — Operations
**Docker images *(implemented and verified)*:** the **Maintenance** page lists the instance's images the way Docker Desktop cannot: one row per server (*Realm server* `worldstone/vanilla-realm`, *World server* `worldstone/vanilla-world`), *Old build* rows, and the *Database server*, each with its image id, size, and the containers running from it (read from `docker container inspect`, so a container from any tool counts). *Old build* is an image a newer build replaced and left without a name, or an image under the pre-rename name `worldstone/<instance>` (builds made before each server had its own image). **Remove N old builds** removes only those, only when every server has its own current image and no container uses them, one `docker image rm` each and never `--force`; the current images, the database image and all data are never touched. After a successful build the app also runs `docker image prune --filter label=io.worldstone.instance=<instance>` to drop the build it replaced (Docker refuses an image a container uses; Docker Desktop's newer image store drops the name on its own). Helper images that are not this app's (for example `alpine`) are not listed and never touched. Moving an existing instance to the new names needs one *Build server* (the compile is cached: 12 s) and one restart of the servers; the old `worldstone/<instance>` tags then show as old and can be removed here.

The rest of the **Maintenance** page and the **Logs** page *(implemented and verified in the real app; see Milestone 7 verification and the clean-slate run)*. Each is a button of the app's own; the backend re-checks every rule the page shows, and a control that cannot run is disabled and says why.

- **Services (status dashboard):** one row per container (*Database*, *Realm server*, *World server*): state (Running, Starting, Paused, Stopped, Not created, Not answering, Crashed), the address (`127.0.0.1:<port>`, or "only the servers" for the database), how long it has been up, processor and memory with the limit. State and uptime come from `docker container inspect`, the figures from `docker stats --no-stream`; anything Docker did not give is a dash, never a zero. Read again every 5 s while the page is open; only the newest read is shown.
- **Backups:** *Back up now* writes one gzip'd `mysqldump` per schema (every recipe schema plus the app's own `worldstone` ledger) to `Instances/<id>/Backups/<schema>-<UTC yyyymmdd-hhmmss>-<label>.sql.gz` (written as `.part` and renamed when whole; labels `manual`, `before-update`, `before-restore`, `before-reset`). The files of one run are one backup; the page lists them newest first with the databases each holds and the size. *Open folder* opens the folder. The app never deletes a backup. **Restore** needs the servers stopped and asks for confirmation that says what will be replaced; then it verifies every file (`gzip -t` and the dump's "completed" line) **before anything is dropped**, takes a `before-restore` backup, drops and reloads each schema, and checks every schema has tables. A database that was stopped is started for the work and stopped again. A backup that lacks some schemas restores only those it holds; one holding a schema this server does not have is refused.
- **Logs page:** *Live activity* (what the running operation prints) and *Browse logs*: the launcher's own log (kept between sessions), each container's log (`docker logs`, with Docker's timestamps), and the log files the servers write under `Logs/server`. Choose 200–5000 of the newest lines, filter by text, *Follow* (re-read every 2 s), *Snap to bottom*, *Reload*, *Copy*. Reading a log changes nothing, so it works while an operation runs.
- **Update:** one operation that checks everything first (source ready, image built, database present), fast-forwards the source only (local edits are never overwritten), rebuilds the images only if the source changed, and, if database scripts are waiting and the servers are up, stops them, **backs up all databases**, applies the scripts and starts again. Servers that were stopped stay stopped; if nothing changed nothing is restarted, and the result says so. It cannot be cancelled, because the stop/backup/apply/start sequence must not be left half done.
- **Repair:** lists what is wrong (missing source, an unbuilt image, missing extraction, an incomplete database, missing configuration, unfinished backup files, servers that crashed or stopped answering) and puts right what the app can by running the same steps as Setup (and restarting the servers when one crashed or only some are up). It never deletes or overwrites data: an incomplete database is completed by the normal database step, never reset; a server that is only out of date is left to Update; servers that are stopped, starting or paused are not faults; the only files it removes are unfinished `.sql.gz.part` backups. Problems only the person can fix (for example the client folder they chose) are listed as such. It checks again afterwards and fails, saying what remains, if anything does.
- **Reset this server:** the only place in the app that deletes data. It lists what will go (database, database credentials, generated configuration, server logs, and only if ticked the extracted game data, with sizes) and what is never deleted (source, images, backups, settings, the chosen client). The button enables only after the instance's id (`mangos-zero`) is typed; the id is checked again in the command and in the task. The task stops the servers, takes a `before-reset` backup **and deletes nothing if that fails**, then removes the containers, the database volume, the game-data volume if ticked, and the generated files. Afterwards the instance is where it was before *Set up database*; Setup rebuilds it, and a backup can be restored.
- Every operation that finishes says what it did (for example "Everything was already up to date, so nothing was changed and nothing was restarted.") in the Current operation panel and the log.

## 6. Recipes

Everything emulator-specific lives in `src-tauri/recipes/<id>.toml`; the engine owns the generic steps. A recipe declares: repos (URL, branch, path, submodules), build system and flags, how bots arrive (`in-tree option` | `separate module repo` | `fork + module`), database layout and install order, extraction tools and outputs, config templates and managed keys, ports, supported client builds. A value that reaches a path, command or SQL is validated on load. Only `mangos-zero` is implemented today, but **multiple emulators will be added**, so this is an architecture requirement, not a nicety:

- **No emulator specifics in Rust.** Repos, flags, database layout, extractor commands, config keys, ports and bot mechanism come from the recipe. If a step needs something a recipe cannot express, extend the recipe format; do not special-case an emulator.
- **Multiple instances side by side.** Each instance has its own folder (`Instances/<instance-id>`), Docker Compose project name, container names, volumes, generated credentials and **host ports** (allocated from a range and checked for conflicts; never two instances on 3724/8085). Running one must not require stopping another.
- **Docker naming convention.** Everything the app creates in Docker can be identified at a glance in Docker Desktop:
  - **Images:** `worldstone/<edition>-<role>`, one tag each. `edition` is a recipe field (`edition = "vanilla"`) and `role` is a field of each `[[run.services]]` entry (`realm`, `world`); both are validated as lowercase ids and roles are unique. For Zero: `worldstone/vanilla-realm:latest`, `worldstone/vanilla-world:latest`, and `worldstone/vanilla-database:<public version>` (the database's public image under this name; its tag keeps the public version). A second instance of the same edition inserts its instance id: `worldstone/vanilla-<instance>-world`. There is no code-named or fingerprint tag, because it shows as a duplicate row; the build fingerprint, commit and recipe are labels (`io.worldstone.fingerprint`, `.commit`, `.recipe`, `.playerbots`, `.instance`, `.edition`, `.role`).
  - **Containers, volumes, Compose project:** built from the instance id, not the edition: `worldstone-<instance>-<service id>` (`-db` for the database), `worldstone-<instance>-gamedata` and `-dbdata`, project `worldstone-<instance>`. Volumes hold user data and are never renamed, so these stay keyed to the instance. Known consequence: for Zero the images say *vanilla* while containers and volumes say *mangos-zero*.
  - **A new recipe must set `edition` and each service's `role`** so its images read correctly; nothing else about the names is emulator-specific.
- **A recipe carries its own look.** An optional `[theme]` gives the expansion's `accent` and `deep` colours (`#rrggbb`, validated on load) and an `emblem` name (`swords`, `snowflake`, `flame`, `skull`, `shield`, `crown`, `mountain`, `castle`, `leaf`, `sun`; an unknown name draws a shield). The UI never names an emulator to decide how it looks; without a theme a server keeps the app's blue. Zero is gold on warm brown with crossed swords, AzerothCore icy blue on frozen steel with a snowflake. `backdrop` (`azeroth`, `northrend`) names the scene drawn faintly behind the button: hills under a low sun with a keep for Azeroth, aurora over ice peaks with Icecrown's spires for Northrend; none or an unknown name draws none. The scenes are original SVG shapes in the accent colour (`src/components/ServerArt.tsx`), not game artwork. A new expansion adds its own `[theme]` (and, for a new emblem, one icon in `src/components/ServerButton.tsx` and its name in `src/lib/serverTheme.ts`; for a new scene, a drawing in `ServerArt.tsx` and its name there too).
- **Instance id is not the recipe id.** Today there is one instance per recipe and the instance id equals the recipe id; that limitation must be lifted (create-instance flow choosing a recipe and a name) before a second emulator, or a second server of the same emulator, is added.
- **Adding an emulator** = a new recipe plus any new generic capability it needs. It is listed as supported only after passing §9 with bots on and working.

## 7. UI requirements

- **Look:** dark charcoal panels, thin slate borders, blue for primary actions and progress, green ready, amber attention, red error, gray unknown; modest radii; Lucide icons; readable at 1280×720+.
- **Layout:** left sidebar with the app name and version (from app metadata) at its top, and card-based content that starts at the top of the window. **There is no full-width top bar**: it held only the name and version, and the rest of it was empty space the content could use (the window already has its own title bar). Sidebar lists only pages that exist. **Status cards are compact** (icon, title and status on one line, the detail under it, about 17 rem wide minimum, as many columns as fit), so a wide window shows the whole state at a glance and the log gets the room; a card never takes more height than its two lines of detail.
- **Status bar:** one thin line (28 px) along the bottom of the window, on every page, showing only state the launcher already reads. Left: the server state with how long this run has been going (the most recently started service), and the bots ("84 bots · 1 player"; left out while the servers are stopped). Middle: the running operation with its own step and percentage (a moving bar when it reports none; never a made-up number), **Cancel** where the operation can be cancelled, and, when the launcher is inside *Set up*, "Set up, step 3 of 5: …". Clicking it opens Logs. When nothing runs it says *Idle*, or the last failure, or "Restart needed to apply the changed settings", or the last cancel, in that order of priority. Right: Git/Docker readiness (the first thing that is wrong, else "Docker ready"; this replaced the sidebar's "Launcher ready" footer), the age of the newest **complete** backup (amber when there is none, none complete, or the newest is over a week old; not shown before the database exists), and the realm list address the launcher writes into the game client, with a copy button. Colours: red and amber only where something needs a person; a stopped server is grey, not an error. Unknown is shown as unknown ("Server state unknown", "Bots unknown", "Backups unknown"). Narrow windows drop items instead of wrapping: below 1100 px the address goes, below 1000 px the backup age goes. Not shown, on purpose: CPU and memory (Maintenance has them), "update available" (nothing checks for one), anything decorative. The decision logic is `src/lib/statusbar.ts` (tested); the component is `src/components/StatusBar.tsx`.
- **Server picker:** the sidebar's *Server* list has one button per recipe, themed to its expansion from the recipe's `[theme]` (§6): an emblem tile, the name in the *Server names* font (Settings, below; Segoe UI unless changed), the game line in the accent colour, a fade from the dark tint, the expansion's scene faint behind it (fading out toward the text, stronger on hover and on the chosen one), and, on the chosen one, a bright accent edge, border and glow. The game line wraps rather than truncates, so "Wrath of the Lich King 3.3.5a" is always readable. Disabled, with the reason, while an operation runs. Painting is `.server-btn` in `src/styles.css`; the values are checked in `src/lib/serverTheme.ts` (tested).
- **Settings:** a small gear at the bottom of the sidebar opens a settings window (a dialog with Esc, an X and click-outside to close, focus kept inside while it is open). It has a tab rail on the left, so more kinds of settings are one entry in `TABS` (`SettingsDialog.tsx`) and one component; it lists only tabs that exist. There is one tab today:
  - **Fonts.** A **font role** is a place text appears. The roles are *General UI* (everything in the window) and *Server names* (the names on the server buttons). **Every role gets the same controls, and any new role must too: this is the standard.** A role has a **font** (from *Installed on this PC*, or *Google Fonts*), an optional **outline** (width 0–8 px, colour, opacity) and an optional **shadow** (across and down −40…40 px, blur 0…60 px, colour, opacity), each with a switch and its controls disabled while it is off. A live preview draws the role's own sample text. **Reset** puts the role back to the standard: **Segoe UI, no outline, no shadow**, and is disabled, with the reason, when it already is. Changes show everywhere at once and are saved about 0.35 s after the last one, with "Saving… / Saved / Not saved: reason" beside them. A role is one entry in `FONT_ROLES` (`src/lib/appearance.ts`), one field in `FontSettings` (`appearance.rs`) and the CSS that reads its variables `--font-<role>`, `--stroke-<role>`, `--shadow-<role>`.
  - *Installed on this PC* lists every font family Windows has (read in the background when the app starts, so it is ready when the window opens; refreshable), each name drawn in its own font, with search. A chosen font that is no longer installed says so and shows Segoe UI instead.
  - *Google Fonts* lists Google's families by popularity (the 100 most popular; search reaches all of them). Each name is drawn in its own font as its row scrolls into view (a small preview from Google, below), so the list shows what the fonts look like before anything is downloaded. Choosing one **downloads it to this PC once** (regular and bold, or the nearest weights it has) and it works offline from then on; a *Downloaded* tag marks the ones already here. *Add by name* downloads a family that is not in the list. *Refresh* fetches the list again; if that fails the last list is kept and the reason is shown. If the files of the chosen family cannot be read, the window says so, text uses Segoe UI, and *Download again* is offered.
- **Behavior:** a button that starts work changes state immediately (spinner + disabled), long work reports steps and real progress, cancellation only where safe, errors are readable with details in the log, no blocking dialogs for routine progress, confirmation only for destructive actions.
- **Home header:** the first thing on Home is a header card with the app name and the recipe's name and game, on a **themed, faded background** (the accent and gold of the palette as soft glows over a faint diagonal texture, with a large gem outline fading out to the left; drawn in CSS and SVG icons, no bundled artwork or game assets, so it follows the palette and costs nothing to load). It carries the controls people use every day, so they are not hidden in a step list:
  - **Set up**: runs every step that is still missing, in the order they depend on each other (*Download source*, *Build server*, choose the game client, *Extract client data*, *Set up database*, *Generate configuration*), using the same commands as the step buttons. It re-reads the real state before each step, so it resumes, skips what is done, never repeats a step, and never runs an update the person did not ask for (an existing source download is not updated, a ready database is not touched). It stops at the first failure or cancel (the task panel says why), stops with the reason when a step is blocked (Docker not running, a database schema this app did not create), and opens the folder picker when no game client is chosen (closing it stops the chain). It ends at *ready to start*; starting the servers stays a separate click. Disabled, with the reason, while another operation runs, while a step is blocked, and when everything is already set up.
  - **Start servers**, **Pause servers** (which becomes **Resume servers** while they are frozen), **Restart servers**, **Stop servers** (Step 6).
  - **Launch game** (Step 7): starts the chosen client so it logs in here.
  - Every one of them is disabled, with the reason as its tooltip and in the list under the cards, when it cannot work; none is a placeholder.
- **Where the game client is configured:** the client is chosen once and remembered per instance (Step 3): *Choose client* / *Change client* on Home, *Browse…* or a pasted path on Setup. Its `realmlist.wtf` is handled by *Point client* / *Restore* on Play, and *Launch game* points it too (see Step 7). There is no other client setting: what a usable client is comes from the recipe's `[client]` section.
- **Each step page** shows: its state, what it will do, its actions, its last result, and, if it failed, the reason and the next action.

## 8. Data and storage

`Instances/<id>/{Repos,Data,Config,Logs,Backups,Temp,Docker}` under the launcher directory (dev: project root; packaged: the executable's folder; `WORLDSTONE_HOME` overrides). App-wide files sit beside `Instances`: `Settings/appearance.json` (the font roles, outlines and shadows; a missing file means the defaults, an unreadable one is moved aside to `appearance.broken-<time>.json` before anything is saved over it, and every save is written to a `.partial` file and renamed) and `Fonts/` (`google-catalogue.json`, the last Google list, and `google/<family>/` with the downloaded font files and a `font.json`). Both are per person, not per server, and are git-ignored. Database files and extracted client data live in Docker named volumes or under `Data`, never on a path that crosses the WSL boundary in a slow way. Generated credentials live in `Config` and are redacted from all logs.

## 9. Definition of done and acceptance

A step is done only when **its own tests pass and its buttons have been exercised in the real desktop app** on a machine with a clean instance. The acceptance run for the Zero milestone:

1. Clean instance → Step 0 all green.
2. Download source → both repos Ready with all submodules.
3. Build → images exist; `aiplayerbot.conf.dist` present.
4. Select a real 1.12.x client → extraction completes → four data folders populated.
5. Provision database → every schema at the newest `db_version`; bot tables present.
6. Configure → managed keys correct; a hand-edited key survives a re-run.
7. Start → both ports up; console responds.
8. Create an account through the app → a real client logs in and enters the world.
9. **Bots online count reaches the configured minimum and survives Stop/Start.**
10. Update source (no change) is a fast no-op; Stop is graceful; nothing was deleted.

Automated tests cover parsing, planning, safety rules and state logic. They do not replace the acceptance run.

### Decisions recorded while building Milestones 4–6

- Default bot population is machine-scaled (settings above), not a fixed preset.
- Ports are published on `127.0.0.1` only; exposing the server to the LAN is deferred to Milestone 8 (it also changes the realm row and needs a warning about exposure).
- *Stop servers* stops the database as well, so nothing keeps running in the background after the user stops. *Start* brings it back.
- *Start* recreates containers to match the compose file and never deletes volumes. (A separate *Repair* was added in Milestone 7; see Step 9.)
- `PlayerbotAI.DisableBots = 0` is managed only so the start-up banner agrees with the running random bots.
- Accounts go through the console and are confirmed in the database; default accounts are detected by hashing and warned about; `RNDBOT` names are reserved; the password character set is narrower than the game allows so nothing is read specially by the console or the command templates.
- Bot health is stateless (database counts + uptime, 10-minute grace) so a page reload or an app restart never changes what is shown; saving bot settings never restarts the servers by itself.
- The server's own GM log is disabled because it would keep new passwords in plain text.
- The realm list convention is line-level (change one line, keep a never-overwritten saved copy, restore only that line).

### Decisions recorded while building Milestone 7

- **Backups include the app's own ledger schema** (`worldstone`), so a restore returns the record of which database scripts were applied together with the data; restoring the game databases alone would leave the two disagreeing.
- **A restore verifies before it drops.** Every file is tested (`gzip -t` and the "Dump completed" line) before the first `DROP`, because a truncated dump discovered halfway would leave a half-restored database. A `before-restore` backup is always taken, so a restore can itself be undone.
- **Update cannot be cancelled** (unlike Build): stopping in the middle of stop → backup → apply scripts → start would leave the database and the servers out of step.
- **Repair never deletes or overwrites.** It completes a database through the ordinary database step (which only adds what is missing) rather than resetting it, and treats "outdated but working" as Update's job, not a fault. The person's client choice is reported as something only they can change.
- **Reset is the only deletion, is typed-confirmed in three places (page, command, task), and backs up first.** If the `before-reset` backup fails nothing is deleted. It keeps the source, images, backups, `settings.json` and `client.json`, and keeps the extracted game data unless it is ticked, because extraction takes far longer than anything else Setup does.
- **Reset was first run for real in the clean-slate run** (below), after the owner agreed to it; until then it was covered only by tests against temporary folders.
- **A task can say what it achieved.** `Task::outcome` stores a line as the success message of the finished task, so "already up to date, nothing restarted" appears in the panel and log instead of a bare "Finished".
- **Reads that change nothing are allowed while an operation runs** (logs, the service table); status blocks that describe what an operation is about to change are not re-read until it ends.

### Decisions recorded while building the status bar

- **It shows the realm list address, not `host:port`.** The recipe does not say which service the client logs in to, so guessing the first service's port would put a fact the app cannot back into a fixed spot. The address is what the launcher itself writes into `realmlist.wtf` (the client uses its own default login port).
- **A stopped server is grey.** The Home cards' generic "Stopped" status is red; on a bar that is always visible, a server the person stopped on purpose should not look like a fault. Red is kept for a failing server, a missing dependency and a failed operation.
- **The backup age is read when the app starts and after every operation, not on a timer.** Backups are only made by the app's own operations, and reading them asks Docker two questions; the age itself is recomputed every 30 seconds. The one-week threshold for amber is a nudge, stated in the item's hover text, not a rule the app enforces.
- **A failed operation outranks "Restart needed"** in the middle of the bar, because it is the fresher fact and the error is otherwise easy to miss on a page that does not show the task panel; the restart hint returns as soon as the next operation starts and ends.
- **The bar is honest when the app runs in a plain browser:** it says "Desktop app only" and nothing else, as the sidebar footer did.

### Decisions recorded while building Milestone 9

- The importer, not the app, creates AzerothCore's tables and applies its updates; the app only creates the empty schemas and the account, backs up first (whenever a finished import exists), runs `dbimport` in a throwaway container, and verifies the result (§4.3). ### Decisions recorded while making status reads fast (2026-09-29)

- **Why:** each status card started several `docker` processes (0.3–0.6 s each, up to a dozen at once), so a page took 5–9 s to fill in. Reading Docker's engine API directly makes the same reads take 5–70 ms; see §5, Step 0, "Reading Docker".
- **Accuracy over speed:** per-object reads are never reused; the few shared reads obey the freshness rule in Step 0. The tests cover that an answer gathered before a change is dropped, and the real-app check below covers a change made by the app and one made outside it.
- **Git is asked concurrently, never remembered.** The independent questions of one status (`log`, `status`, `submodule status`, one checkout per repository) run together. `git submodule status --recursive` (about 0.8 s on Windows) is skipped only for a checkout with no `.gitmodules` and no submodule in Git's index, where it prints nothing anyway; the digest of the source, and so the image fingerprint, is byte-for-byte what it was, so no image was made stale by this change.
- **Polling:** servers are re-read every 3 s (was 10 s) and the other cards every 10 s (was 30 s), both while nothing runs, and everything is re-read when the window is focused or shown again (at most every 2 s). Reads are cheap enough for this; the point is that what is on screen was true a moment ago, not that it is refreshed a lot.
- **Compose's version** is keyed to Docker's program file and the engine's version, since it ships inside Docker Desktop. A Compose plugin replaced on its own, without Docker changing, shows after the app restarts.
- **Still through the `docker` program:** every change (build, start, stop, pause, import, extract, remove, tag) and the streaming reads (container logs, resource use on Maintenance).

- **Installed fonts** are listed with a short PowerShell script (passed as an encoded command through `process.rs`) that asks WPF for `SystemFontFamilies` by their English names; the composite `Global *` families are dropped. Starting PowerShell takes a moment, so the list is read once per session and cached until *Refresh*.
- **Google Fonts** has no official list endpoint without an API key, so the list comes from the metadata endpoint that fonts.google.com itself uses (`https://fonts.google.com/metadata/fonts`, undocumented, so it can change) and is cached in `Fonts/google-catalogue.json`. *Add by name* is the way round it if the list ever cannot be read. Files come from Google's `css2` stylesheet and only from `https://fonts.gstatic.com/`, with a ttf/otf/woff/woff2 name; each is checked by its first bytes before it is kept, downloaded into a `.partial` folder and swapped in only when complete. `curl.exe` (part of Windows 10 and 11) does the downloads, because it needs no extra dependency and uses the system's proxy and certificates. Downloads are one at a time.
- **Google fonts are handed to the page as bytes** (`FontFace` from base64), not by URL, so a chosen font works offline. The one thing the page fetches from Google itself is the **list previews**: for a row on screen it asks Google's stylesheet for only the letters of that family's name (a few hundred bytes of CSS and a few KB of font, from `fonts.gstatic.com` only, once per family per session) and registers them as `ws-preview <family>`, a name that can never shadow the real download. Offline, or if Google refuses, the row simply stays in the UI font. Choosing a font is unaffected.
- **Validation:** a Google family is letters, digits, spaces and hyphens (60 characters at most); an installed name has no control characters and none of `"\;{}<>`; colours are `#rrggbb`. When the CSS is built the quote, backslash, semicolon, braces, angle brackets and line breaks are also removed from a font name, and a colour that is not `#rrggbb` becomes black, so a bad value in the file cannot break out of a style.
- **The outline width is doubled** in CSS: the stroke is drawn behind the letters (`paint-order: stroke fill`) so only its outer half shows, and the slider then means what the outline looks like.
- The general font, outline and shadow are set on `body` and inherited; the server names override them with their own variables. The code font on the log panels (Cascadia Mono) is not a role.
